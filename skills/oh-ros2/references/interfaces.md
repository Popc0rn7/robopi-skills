# 仿真与真实设备的接口对齐

用于把 Gazebo/PX4 等模拟输入替换为硬件输入，或设计 ROS 驱动与定位模块的边界。接入设备不意味着自动获得其定位或控制能力。

## 定义共同契约

记录每种输入/输出的消息类型与版本、topic、单位、坐标系、时间戳来源、频率/QoS、有效性标志及失效动作。驱动/仿真适配层提供共同契约，上层处理逻辑保持一致。

明确世界坐标、地图坐标、飞控局部坐标及传感器安装坐标的关系。ENU/NED 和 FLU/FRD 只在明确适配边界转换，不能按名字推断原点相同。几何世界坐标不是 GNSS 经纬度；经纬度转换还需参考原点、地理/高度基准及局部定位参考。

模拟 `/clock` 与真实采集时间采用各自时源，但上层遵守相同的新鲜度和同步要求。不要要求两者使用相同绝对 epoch，也不要用替换来源偷偷改变超时逻辑。

## 区分数据来源与处理算法

| 已有输入 | 真实替代 | 要核对的处理边界 |
|---|---|---|
| Gazebo 点云 | 实际雷达驱动 | 坐标、安装外参、时间戳、点云字段与 QoS |
| 模拟 IMU/GNSS | 硬件驱动 | 是否实际接入融合模块、时间同步及噪声/有效性语义 |
| PX4 SITL 里程计 | 飞控或外部定位 | 同一定位来源策略、reset 语义和坐标基准 |
| PX4 SITL 控制接口 | 真 PX4 飞控 | 消息/固件匹配、连接方式、飞控拒绝和失联处理 |

直接使用 PX4 估计里程计，与在算力板上融合 IMU/GNSS 是不同架构。未经实现和验证，不称“所有传感器只换驱动即可”。同样，发布原始 GNSS 话题不证明 GNSS 已参与定位。

PX4 uXRCE-DDS Client ↔ MicroXRCEAgent ↔ ROS 2 是桥接链路；Wi-Fi/Ethernet/串口是传输选择。Agent 在主机还是板端需明确并单独验证，不能因算法迁移成功就声称 Agent 已迁移。

## 对照与范围

用相同任务输入和坐标契约比较仿真适配与硬件适配。先做录制/合成数据、消息与坐标验证，再按授权做物理仿真或设备运行。

输入被安全拒绝、输出正确生成、执行完成和未知区域安全是不同结论。一次静态场景或通信停滞测试不能证明真实无线断开恢复、自动探索、SLAM 或任意场景的自主导航。

涉及固件配置、驱动 API 或具体传感器的新版本时查当前项目源码/官方资料，不从历史案例推断支持。这个参考提供接口决策，不提供未验证的 GNSS/IMU 融合实现。
